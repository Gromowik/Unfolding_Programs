Это уже готовая программа правда, а не модель - # Техническое задание (ТЗ)

Проект: личная система памяти мастера для ремонта техники/авто  
Версия: 1.0 (MVP)  
Дата: 2026-06-03  
Стек реализации: Next.js + React + TypeScript + Tailwind

## 1. Цель проекта

Создать веб-приложение, которое превращает поток практического ремонта (фото, видео, аудио, текст) в структурированные шаги, пригодные для повторного использования, анализа и формирования личных инструкций.

Ключевой принцип:

1. Данные хранятся плоско.
2. Структура формируется динамически под текущий запрос пользователя.

## 2. Границы MVP

### Входит в MVP

1. Создание кейсов ремонта.
2. Добавление шагов ремонта в кейс.
3. Прикрепление медиа к шагам.
4. Ручная тегизация и фильтрация шагов.
5. Поиск по тексту и тегам.
6. Генерация краткого конспекта кейса (LLM).
7. Просмотр истории кейсов и шагов.

### Не входит в MVP (этап после MVP)

1. Полноценный граф знаний и авто-онтология.
2. Коллаборация в реальном времени для команды.
3. Продвинутая аналитика ошибок по множеству мастеров.
4. Мобильные нативные приложения.

## 3. Роли пользователей

### Роль 1: Мастер

1. Создает кейсы.
2. Фиксирует шаги ремонта.
3. Ищет прошлые похожие ситуации.
4. Получает авто-конспект по кейсу.

### Роль 2: Администратор (базово)

1. Управляет аккаунтом и доступом к данным.
2. Просматривает системные журналы (при необходимости).

## 4. Основные пользовательские сценарии

### Сценарий A: Новый ремонт

1. Пользователь создает RepairCase.
2. Добавляет StepAtom по мере работы.
3. Для каждого шага прикладывает фото/видео/аудио/текст.
4. В конце получает краткий структурированный отчет.

### Сценарий B: Поиск повторяющегося кейса

1. Пользователь вводит симптомы или выбирает теги.
2. Система выдает релевантные кейсы и шаги.
3. Пользователь открывает кейс и повторяет проверенный путь.

### Сценарий C: Рефлексия

1. После завершения ремонта пользователь отмечает ошибки/удачные решения.
2. Система сохраняет эти выводы как часть базы личного опыта.

## 5. Функциональные требования

### 5.1 Кейсы

1. Создать, редактировать, закрыть кейс.
2. Поля кейса: устройство/авто, модель, симптомы, статус, заметки.
3. Список кейсов с фильтрами по статусу и дате.

### 5.2 Шаги (StepAtom)

1. Добавить шаг в кейс.
2. Указать: заголовок, действие, ожидаемый результат, фактический результат.
3. Проставить теги (узел, инструмент, тип операции, ошибка, проверка).
4. Поддержка упорядочивания шагов по времени.

### 5.3 Медиа

1. Загрузка фото/видео/аудио.
2. Привязка медиа к шагу.
3. Хранение метаданных: тип, размер, длительность, дата.
4. Предпросмотр медиа в карточке шага.

### 5.4 Поиск и фильтры

1. Поиск по заголовкам и тексту шагов.
2. Фильтрация по тегам, узлу, инструменту, типу проблемы.
3. Сортировка по релевантности или дате.

### 5.5 Генерация конспекта кейса

1. Кнопка "Сгенерировать конспект" для завершенного кейса.
2. LLM формирует блоки:
   1. Симптомы.
   2. Диагностика.
   3. Выполненные действия.
   4. Итог и рекомендации.
3. Пользователь может отредактировать и сохранить конспект.

### 5.6 Аутентификация

1. Email + пароль (или OAuth на выбор команды).
2. Доступ только к собственным данным (single-user mode в MVP).

## 6. Нефункциональные требования

1. Время отклика UI для основных действий: до 300 мс (без учета загрузки больших файлов).
2. API-ответы для CRUD-операций: до 500 мс при нормальной нагрузке.
3. Безопасность: валидация входных данных и контроль доступа к файлам.
4. Надежность: отсутствие потери данных при частичном сбое запроса.
5. Масштабируемость: подготовка к переходу на multi-user после MVP.

## 14. Критерии приемки MVP

3. Поиск находит шаг по ключевому слову и тегу.
4. Конспект кейса генерируется и сохраняется без ошибок.
5. Данные одного пользователя недоступны другому.

/models/core/flow.ts
ts
export interface FlowStep<T> {
  value: T;
  next?: FlowStep<T>;
}

export function createFlow<T>(steps: T[]): FlowStep<T> | null {
  if (steps.length === 0) return null;

  let head: FlowStep<T> = { value: steps[0] };
  let current = head;

  for (let i = 1; i < steps.length; i++) {
    current.next = { value: steps[i] };
    current = current.next;
  }

  return head;
}

export interface Equilibrium {
  matched: boolean;
  score: number;     // степень совпадения
}

export function computeEquilibrium(staticScore: number, dynamicScore: number): Equilibrium {
  const score = Math.min(staticScore, dynamicScore);
  return {
    matched: staticScore === dynamicScore,
    score
  };
}

У нас еще сформировалось представление, что, само фото как Д1 казалось бы проще, но в отличии от текста, который нам интуитивно кажется больше чем просто одно фото, не есть Д, а есть сфокусированное ядро Г.
Это ядро, центр как Г, может иметь хоть и одно Д1 с другими Г, но тем не менее имеет свое Д2 AttentionZone, которое указывает область внимания, как точки релевантные для этого Г. 
Одно Д1 и множество вероятных Д2 от него говорит о нашей попытке совместить к примеру в фотографии множество точек, которое мы сужаем через Д2, которое в свою очередь также есть множество точек внимания, представленных один участком, чтобы описать Г, по сути это попытка отобразить множество точек внимания как единый образ, для простоты, а текст чтобы создать кинетику движения по ним, в которой и проявляется генерализация этих точек. 
Кинетика особенно важна для ремонта, чтобы не стоять и не анализировать всю картину, а знать с чего начинать.
